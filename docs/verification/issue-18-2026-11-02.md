# Issue #18 — indexed MCP discovery (2026-11-02)

## Selection and implementation plan

The current v0.3.0 dependency graph has #12–#17 completed. #18 is the next
high-priority feature, unblocking #20 and #29; #19 can independently automate the
existing backend's cluster checks. #11's two-judge relevance work remains open:
fixture assertions are not human relevance judgments or measured quality gains.
Each selected issue gets its own topic branch and PR into `develop`, per
CONTRIBUTING.md. This branch is `feature/18-indexed-search-mcp`, from develop
`6161245`.

1. Extend `search_tuik`, preserving its name, query/limit inputs, `results` and
   `resource_type`; keep eight tools. Use the optional metadata index by default
   and expose an explicit `live=true` portal path for wider/current coverage.
2. Validate kind, exact full theme, advertised downloadability and inclusive ISO
   date bounds before I/O. Retain direct live service search for backend fallback
   and baseline measurements, preventing recursive routing.
3. Carry scores, highlights, per-hit provenance and indexing times through MCP.
   Aggregate kinds/themes across the filtered full match set, not just the page;
   expose bounded buckets, omitted terms and distributed count uncertainty.
4. Report the actual source/backend, unavailable capabilities and ignored filters.
   Preserve unknown portal totals/truncation as null. Dataset-only fallback uses
   the literal catalog; other fallback requests use the portal.
5. Verify actual stdio transport, fresh-session stable ID resolution, refusal /
   missing-alias / malformed-facet / timeout paths, and real OpenSearch behavior.
